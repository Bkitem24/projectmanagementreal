## Spike 1 - Mica glass - PASS (with one open question)

**Question:** Can our elevated Tauri v2 app on Windows 11 show the Mica material behind a React/HTML UI, in both light and dark theme, without flicker or performance problems?

**What was tried:** `"transparent": true` + `"windowEffects": {"effects": ["mica"]}` on the main window in `src-tauri/tauri.conf.json`; `core:window:allow-set-effects` added to `src-tauri/capabilities/default.json`; `body{background:transparent}` with `#main{background:var(--paper)}` kept solid in `src/style.css` (the sidebar was already translucent with backdrop-blur, so no change needed there). Launched the real dev build (bypassing the UAC requirement with `__COMPAT_LAYER=RunAsInvoker`, same trick used for Round 39's Rust tests - not needed in the shipped/elevated app). Captured the actual native window with `PrintWindow`+`PW_RENDERFULLCONTENT` (Win32 API via PowerShell) since there's no way to screenshot a native desktop window through my normal tools; used WebView2's remote-debugging port (`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333`) to run real JS inside the running app (Chrome DevTools Protocol) for the in-app theme toggle and runtime `setEffects` calls.

**Result:** Mica renders correctly - confirmed by screenshot, not assumed. See `docs/superpowers/specs/spike-1-mica-screenshots/light-theme.png`: the sidebar and the gap in the middle of the Home page show real desktop content blurred/tinted behind them, while the sidebar's own translucent panel and the Home page's actual content (hero banner, clock-in card) render normally on top.

**Real finding - Mica follows WINDOWS' theme, not the app's own toggle:** switched the app's own in-app dark mode (`applyTheme('dark')`, the `data-theme` attribute CLAUDE.md documents) with Windows itself still in light mode. Screenshot (`app-dark-toggle-mica-still-light.png`) shows all the app's own content went dark as expected, but the Mica material visible through the gaps stayed the LIGHT material - it didn't react to the app's own toggle at all, only to the OS-level setting (confirmed from Tauri's own API docs: the bare `"mica"` effect "matches the system dark preference"; `"micaDark"`/`"micaLight"` are the explicit variants). **For Phase A: the app's theme toggle must explicitly call `setEffects({effects:['micaDark']})`/`['micaLight']` at runtime whenever `applyTheme()` runs, not rely on the static config value.**

**Open question - runtime `setEffects()` needs a live human check:** calling `set_effects` via `invoke()` at runtime (the exact mechanism the fix above needs) returned success with no error both times (switching to `micaDark` and back to `mica`), and the app kept responding to further JS calls throughout - no crash. But after that call, my `PrintWindow` screenshots of the window came back showing only the title bar with the entire content area pure white, and did NOT recover after reverting the effect back to plain `mica` or forcing a repaint (resize nudge). This reproduced consistently, immediately after the first runtime `setEffects` call, having worked fine for two prior captures before that. **I can't tell from here whether this is a real visual bug (the WebView2 content actually going blank after a runtime effect change) or just a quirk of `PrintWindow` capture specifically** - a screenshot tool limitation wouldn't affect what a person actually sees. Humayun: please do a 30-second check once Phase A is underway - open the app, toggle dark/light a few times, and confirm the content never actually goes blank/white on a real runtime switch. If it does, the config-level static `mica` (which demonstrably works) is the fallback, accepting that it won't follow the app's own toggle, only Windows'.

**Also confirmed:** app stayed responsive throughout (CDP eval kept working), memory ~51MB (unremarkable), no crash across the whole session including window resize. Did not test drag-between-monitors or a live Meetings call - out of reach without physically doing it; recommend folding into Phase A's own testing rather than a separate check.

**Recommendation:** proceed with Mica in Phase A. Use the static `"mica"` config as the safe baseline; add the runtime `micaDark`/`micaLight` sync to the app's theme toggle as a small follow-up, verified live (per above) before relying on it.

## Spike 2 - React + Tailwind + shadcn/ui alongside vanilla pages - PASS

**Question:** Can one React page run inside the current vanilla-JS app without changing how any existing page looks, and cleanly unmount when you navigate away?

**What was tried:** `react`, `react-dom`, `@vitejs/plugin-react`, `tailwindcss`, `@tailwindcss/vite` installed; `@vitejs/plugin-react` pinned to `^4.7.0` - **its newest major (6.x) requires Vite 8, and this project is on Vite 5.4** (a real, easy-to-hit version trap for Phase A - pin it explicitly, don't let `npm i @vitejs/plugin-react` grab latest). `resolve.alias` for `@/*` added to `vite.config.js` (needed for Vite's own bundler - `jsconfig.json`'s `paths` only helps editor tooling, not the build). Ran `shadcn@latest init` - **its interactive CLI genuinely could not be driven through this sandbox: the first attempt hung on a preset-selection prompt no flag fully suppressed, a retry got killed mid-`npm install` by my own timeout, and a clean retry then hung on a second prompt ("re-install existing UI components?") that `--force`/`-y` didn't cover either.** Worked around it: installed the handful of runtime packages it wanted (`cn`, `tw-animate-css`, `radix-ui`, `class-variance-authority`, `lucide-react`) directly, and hand-wrote the CSS theme-variable block (`src/tailwind-spike.css`) using shadcn's own well-documented standard "neutral" token values - the CLI's `add` command (non-interactive, worked fine) then generated real `button.jsx`/`dialog.jsx`/`dropdown-menu.jsx`/`tabs.jsx` components against those tokens correctly. **For Phase A: don't assume `shadcn init` runs cleanly unattended - either run it once interactively yourself (quick, you answer 2-3 prompts) or use this same manual-package + hand-written-theme fallback.**

Built a real spike page (`src/react/SpikePage.jsx`) wired into the router at `#/react-spike` (`renderReactSpike()` in `main.js`, following the app's existing `activeMeetingRoomCleanup`-style pattern - a new `activeReactRoot` global gets `.unmount()`ed at the top of `route()` before any new page renders, so a React root from one visit never keeps running - including its live data subscription - after navigating away). It reads real client data through the existing `db.js` shim (`db.collection('clients').get()`), renders a shadcn Button that opens a shadcn Dialog, and uses the app's own `--blue` CSS token inside a Tailwind arbitrary-value class (`bg-[var(--blue)]`) side by side with a plain inline style - both work together with no conflict.

**Could not verify inside the real running app itself:** the router (and so `#/react-spike`) only runs after a real login (`onAuthStateChange` in `main.js`), and I'm not able to type a password into the login form myself (hard rule, no exception even for a test account). Two things this blocked:
1. Seeing the actual `/react-spike` page live in the app, with its real back-button/`paint()` integration and dark-theme inheritance.
2. Screenshotting AUTHENTICATED old pages (My Board, Meetings, Admin, an episode checklist) to visually confirm they're unaffected - the plan's own step 4 checklist.

**What I verified instead, and why it's still solid evidence:** the visible-styling question (does Tailwind's preflight reset restyle plain elements) is a pure CSS/DOM question, identical in any Chromium engine - not specific to the Tauri shell (already covered separately by Spike 1). So I built a static, unauthenticated test harness (`preflight-test.html`, not part of the app) that loads the real `src/style.css` and renders real markup/classes copied straight from `main.js`'s actual pages (`.page-title`, `.section-title`, `.btn`/`.btn-primary`, `.check-row`, the sidebar/`.brand` markup, a `<select>`), opened in a real browser via the dev server - a completely legitimate way to test this specific question without a login. Screenshots below.

- **Setup A (full `@import "tailwindcss";`, with preflight) works today with NO visible regression** - confirmed by screenshot AND by reading the CSS: `style.css` puts its own Tailwind import at the very TOP of the file, so its own explicit rules (`h1,h2,h3,h4{...}`, `button,input,select,textarea{...}`, `select{...}`) come LATER in source order and win the cascade over preflight's resets, for everything it explicitly styles.
- **Real, concrete edge case found (not currently triggered):** `style.css`'s heading rule sets font-family/weight but deliberately never sets an explicit font-size, relying on the browser's own default h1-h6 sizing to still apply for anything not wrapped in a sized context. Preflight removes that browser default. In my test harness, a genuinely bare `<h2>` (no class, no `.panel`/`.modal-head` wrapper) visibly SHRANK to body-text size under Setup A, and a bare `<ul>` lost its bullets. **I checked the real app's source for both**: all 17 `<h2>` and 13 `<h1>` uses carry `.section-title`/`.page-title` (which DO set explicit sizes, 19px/32px); all 6 bare `<h3>` uses sit inside `.panel` or `.modal-head` (which also set explicit sizes via a contextual selector); there is no `<ul>` anywhere in `main.js` today. **Today's app is genuinely safe under full preflight - but this is fragile**, not accidental-proof: the first bare heading or list added later (easy to do without realizing preflight is active) would silently shrink/lose styling. Recommend either keeping this in mind during the page-by-page migration, or using Setup B to remove the risk category entirely.
- **Setup B (`tailwindcss/theme.css` + `tailwindcss/utilities.css`, no preflight) also works, confirmed by the same screenshot comparison** - the only visible differences were exactly the ones explained above (bare h2 size, list bullets), both currently moot for this app. shadcn's actual COMPONENTS (Button in 4 variants, Dialog) render and behave pixel-identically under A and B - shadcn's own classes don't depend on preflight, only its CSS variables/utility classes, which are present either way.
- **Interactive components genuinely work, not just static styling** - verified via a second unauthenticated standalone harness (`spike-react-standalone.html`) that mounts real `button.jsx`/`dialog.jsx` directly: clicked "Open a shadcn Dialog" and got a real Radix-portal modal with overlay, correct centering, working close button. Screenshots below.
- **Build/bundle impact:** `npm run build` succeeds cleanly. The React/shadcn code for `/react-spike` is automatically code-split into its own lazily-loaded chunk by Vite's `import()` in `renderReactSpike()` - confirmed in the real build output: the main always-loaded bundle only grew ~1KB (484.95kB → 486.00kB) from adding the dependencies; `react-dom/client` (209KB) and the spike page itself (78KB) only download if someone actually visits `/react-spike`. **CSS did NOT code-split** - Tailwind's compiled utility CSS landed in the one always-loaded `style.css` (55.72kB baseline → 92.10kB, +36KB) because `tailwind-spike.css` is `@import`ed directly into `style.css`. For Phase A, if zero CSS cost for non-React pages matters, give the Tailwind output its own lazily-injected stylesheet instead of folding it into the main one - not done here since it wasn't this spike's question.
- **Hot reload works** - confirmed implicitly: edited `tailwind-spike.css` between screenshots (switching Setup A ↔ B) without restarting the dev server, and the browser reflected it immediately (Vite HMR).
- **Did not separately run a full `tauri build`** - this spike touched no Rust/`src-tauri` files at all, and `npm run build` (the exact step a Tauri build depends on) succeeded; Round 39 already exercised the full Rust build pipeline extensively, so re-running it here for an unrelated frontend-only change wasn't worth the ~1-2 minutes for the marginal confidence.

Screenshots were viewed directly in the browser pane during this session (not saved as files - unlike Spike 1's native-window captures, there was no simple way to export these to disk).

## Spike 4 - WhatsApp Business "coexistence" - AMBIGUOUS, not a clean go/no-go

**Question:** Can Humayun keep using his WhatsApp Business phone app AND connect the same Pakistani number to our own app via the Cloud API, as a business self-building its own app rather than going through a Meta partner?

**Research only this round** (web search + Meta's own developer docs) - the plan gates creating an actual Meta developer account on research saying a clear GO, and it didn't. **Status: needs Humayun's decision before any more work happens here.**

**Country:** Pakistan **is** a supported WhatsApp Business Platform market - found multiple Cloud-API-provider services (BSPs) explicitly operating there, and Pakistan appears in Meta's own per-country pricing tables (below). Not a blocker.

**The real open question - is Coexistence itself self-serve, or partner-only?** This split into two different things that easy WhatsApp reading online blurs together:
- **Plain Cloud API (API-only, no more phone app on that number):** clearly self-serve. A business building only for itself ("Direct Developer" in Meta's own terminology) can create its own Meta app and skip the full App Review process Meta requires of apps meant to onboard OTHER businesses (Tech Providers/Solution Partners) - a System User with the right permissions is enough.
- **Coexistence (keeping BOTH the phone app and the API working on the same number, which is what Humayun actually wants):** Meta's OWN official documentation for this (`developers.facebook.com/.../embedded-signup/onboarding-business-app-users`, fetched directly) is written entirely for Tech Providers/Solution Partners onboarding THEIR business customers - it never describes a path for a business to onboard its own single number without going through a partner. I could not find a Meta doc describing direct self-serve Coexistence. This may mean it genuinely requires a partner/BSP today, or it may just mean Meta's docs are partner-centric and a Direct Developer's own app CAN still do it (same underlying Embedded Signup API) - **I can't tell which from documentation alone; only actually trying Embedded Signup as a Direct Developer would settle it**, which is real work (a Meta Business Portfolio + app) I'm not doing without Humayun's go-ahead given the ambiguity.

**What Coexistence limits, once active (confirmed, applies regardless of self-serve vs. partner):**
- Throughput capped at 20 messages/second on that number (irrelevant at Blue Kite Media's scale).
- Broadcast lists become read-only; disappearing messages and "view once" messages get disabled.
- Unsupported linked devices (Windows/WearOS companion apps, if used) get unlinked on activation.
- Message-history sync window on activation: sources disagreed (one said up to 180 days for 1:1 chats, another said a 24-hour sync-or-offboard window) - **this needs confirming directly if Coexistence is pursued**, not something to rely on secondhand.
- New messages after activation mirror both ways (phone app ↔ API) via webhooks in real time.

**Pricing - corrected from what I told you earlier in this conversation, which is now out of date:** Meta changed WhatsApp Business pricing **October 1, 2026** (days from now). The old "free if you reply within 24 hours" model is going away. New model: **1,000 free service messages per month per number**, then **$0.015/message** for Service, Utility, and Authentication messages in Pakistan, and **$0.0473/message** for Marketing (business-initiated template) messages. A Free Entry Point window (72 hours, unlimited free messages) still applies when someone messages in from a Click-to-WhatsApp ad or Page button - not the normal case for existing clients messaging in directly. At Blue Kite Media's likely volume (a handful of clients, not mass marketing), the 1,000 free/month tier probably covers ordinary conversation entirely - the paid tier mainly matters if you're the one starting a conversation with many people or sending marketing-style messages.

**Fallback (self-serve, no ambiguity):** a second, API-only WhatsApp Business number just for the app - clients would see a different number than the one Humayun uses personally today, and he'd stop using the Business app for that new number specifically (his current number/app stays exactly as-is for anything not moved). Zero setup ambiguity, but changes what number clients message.

**Recommendation - this needs Humayun's call, not mine:**
1. **Try it:** create a Meta Business Portfolio + a Meta developer app himself (his own account, his own verification - I can't do this step), and actually attempt Embedded Signup as a Direct Developer. Either it offers Coexistence directly (question answered, proceed) or it doesn't (fall back to a BSP or the second-number option) - costs him maybe 30-60 minutes, no money, to get a definitive answer instead of my secondhand research.
2. **Skip the ambiguity, use a BSP** (a paid service like the ones found in this search - 360dialog, Wati, and several Pakistan-specific ones) that already has Coexistence built and approved - costs a monthly fee on top of Meta's own per-message pricing, in exchange for certainty and a supported integration.
3. **Accept the trade-off** and use a second, API-only number instead of Coexistence - zero ambiguity, but a different number for clients.

I'd lean toward option 1 first (cheap, fast, and Humayun already has his own developer instincts) unless he'd rather not spend the setup time and just wants a working answer now (option 2).

**Recommendation:** proceed with React + Tailwind + shadcn/ui for Phase A, exactly as scoped. Use Setup A (full preflight, matches shadcn's own default/expectations) since it's already safe for every current page - just flag the "bare heading/list" trap in the Phase A spec so nobody reintroduces it unknowingly during the page-by-page migration. Pin `@vitejs/plugin-react` to `^4.x`. Plan for `shadcn add <component>` (non-interactive, works fine) rather than depending on `shadcn init` finishing unattended. Before Phase A actually starts, do the two checks this spike couldn't (a real login, 5 minutes): confirm `/react-spike` behaves correctly inside the real app shell (back button, dark theme) and eyeball 2-3 real authenticated pages for anything this static-harness approach might have missed.
