### Round 6 (2026-09-21)

- [x] **"The workflow builder is gone" - investigated, it was never actually removed.** The per-client "Workflow templates" section (Client Detail page, Manager/Admin only) was always still there in the code - what actually happened is the per-task "waiting on" edit UI (see below) made it easy to lose track of, since it lived on a completely different page. Fixed two ways: kept it on the Client Detail page for quick access while working on one client, **and** added a brand-new **Workflows** nav item (Admin + Manager only) that lists every client on the left and that client's templates/steps on the right - one place to find and build them from, as asked.
- [x] **Task dependencies redesigned to be defined once, not per sub-task.** This was the bigger ask hiding behind "bring back the workflow builder": a workflow step can now point at another step in the *same template* ("Depends on" dropdown, set from the Workflows page or the Client Detail page's own template section) - every task an episode generates from that step automatically inherits the link, for every future episode, with **no per-task, per-episode "waiting on" entry needed ever again**. The old free-text "waiting on" field (and its per-task edit button) is gone entirely. This is now a genuine **hard block**, matching "if guest is not booked, then none of the tasks can be done" literally: a dependent task's checkbox is disabled - for everyone, including Admin/Manager - until its prerequisite is checked off, and the "Waiting on: X" label is computed live from the real prerequisite task, not a hand-typed copy that can drift out of sync. Also added a guard against an accidental dependency loop (A waits on B waits on A) when setting a dependency, since that would otherwise lock every task in the loop forever with no way out except editing the template again. Needs **schema_v7.sql** (adds `tasks."dependsOnStepId"`; the old `dependsOnLabel` column is left in place, unused, rather than dropped).
- [x] **Team nav removed for Admin, for real this time - with everything it had moved to Admin first.** Admin's "Team" link used to just redirect to the Admin page, making it a second link to the exact same place as "Admin" - now hidden entirely for Admin (Manager's own "Team" link, pointing at their own Team page, is untouched). Before removing it, ported over what the Admin page didn't already have: a "Pending invites" list across *every* team (Admin previously had no visibility into outstanding invite codes at all), each team's own team-scoped services shown (and removable) right on its panel in Admin, and online/offline presence dots on the "All employees" roster to match the look Team Settings always had.
- [x] **Idle detector force-pause, with a warning.** Built on the same global keyboard/mouse hook that already powers screenshot/activity capture (so it correctly notices idle time even when some *other* window has focus, not just idle-inside-this-app): 10 minutes with no keyboard/mouse/click activity shows a clear on-screen warning with a live countdown; 60 more seconds with still nothing clocks the person out automatically, timestamped at the moment activity actually stopped (not "now"), so idle time is never counted as worked time. There's no separate "paused" state in the data model - a force-pause **is** a clock-out, same shape as the existing abandoned-session close-out, and the person just clocks back in via the normal prompt when they're back.
- [x] **Exit confirmation + proper clock-out on close.** Clicking the window's own close ("X") button now always asks for confirmation (message calls out clocking out specifically if currently clocked in), and confirming while clocked in runs a real clock-out (server write, same as the "Sign out" button already did) before the window actually closes - instead of the process just ending outright and leaving the session to be caught later by the heartbeat-staleness sweep. **Revisited round 8 - see below, the confirmation dialog itself had a real bug.** **One judgment call worth flagging:** "I still stayed logged in" was interpreted as "TimeLog still showed me as clocked in," not "my account stayed signed in" - closing the window does NOT sign out of the account (same as any other desktop app staying signed in between launches). **Confirmed correct by Humayun 2026-09-23 - see the Resolved entry above.**
- [x] **App launches maximized by default.**
- [x] **Zoom in/out via hotkey - app-wide, and on the enlarged/lightbox image.** Ctrl/Cmd `+` / `-` / `0` zoom the whole app (same keys as any browser's own page zoom, reset to 100% each launch). The lightbox has its own independent Ctrl/Cmd `+`/`-`/`0` (plus Ctrl/Cmd+scroll-wheel, plus on-screen +/-/Reset buttons for anyone who wouldn't try a hotkey) so zooming an image doesn't also zoom the app behind it. **Panning/Reset were still broken after this round - see round 8.5 below for the real fix.**
- [x] **Image previews blank again in comments/general chat - found and fixed.** Real root cause, not a repeat of the earlier lightbox fix: a file-upload helper (`uploadFile()` in `src/lib/r2.js`) was returning the server's own echo of the storage key instead of the original key it was given - harmless for keys with no special characters, but every real key here has `/` in it, and a `/` survives as a literal `%2F` through a URL's path (confirmed this against how URLs actually parse, not assumed) rather than being decoded back - so the echoed key was already percent-encoded, and reading it back re-encoded it a second time, asking for a key that was never actually stored. A silent 404 dressed up as a blank, non-clickable image. TimeLog's screenshot previews never hit this because that code happened to ignore the echoed value and reuse its own already-known key - now that's the *only* way `uploadFile()` behaves, so this class of bug can't recur at a new call site later. Also quietly fixes the same latent bug in the Client Detail page's "Change photo" upload, which had the identical mistake but hadn't been reported.
- [x] **Connect "failed to fetch" then persistent 404 - diagnosed as far as possible without deploy access at the time.** Added a `GET <worker-realtime URL>/health` endpoint (no login needed) and made every Connect error message include the exact URL it tried to reach. This diagnostic tooling is exactly what cracked round 7's issues below.

### Round 7 (2026-09-21) - Connect fully debugged end-to-end, three separate real bugs found and fixed

Three genuinely different problems stacked on top of each other, found one at a time by actually reading the live repo and a real `wrangler tail` log rather than guessing:

- [x] **File-corruption during manual GitHub edits.** All 12 round-6 files ended up with a stray extra line ("round 6 fixes") appended to the end of the actual file content - the commit-message text had been typed into the file-content editor box instead of the separate commit-message box GitHub shows after clicking "Commit changes...". This alone broke every build ("Couldn't locate or parse tauri config" etc.). Diagnosed by fetching every file directly from the live `main` branch (this repo is public, so its raw file contents are checkable directly) and comparing byte-for-byte against the delivered zip. Fixed once Humayun understood the two separate boxes involved.
- [x] **`VITE_REALTIME_WORKER_URL` was pointing at the wrong Cloudflare Worker.** This project has two separate Workers - `blue-kite-ops-r2` (file uploads) and `blue-kite-ops-realtime` (Connect calls) - and the GitHub secret had the R2 worker's URL in it. That worker genuinely has no `/session/new` route, so it correctly 404'd. Fixed by deploying `blue-kite-ops-realtime` for real and pointing the secret at its actual URL.
- [x] **Cloudflare Realtime's own `/sessions/new` endpoint rejects a request body outright** (a documented quirk other projects have hit too - its schema apparently allows no body at all, and even an empty `{}` fails its validator with a `decoding_error`). `worker-realtime`'s `cf()` helper was always sending `Content-Type: application/json` + a `{}` body for this one call regardless. Found via a real `npx wrangler tail` log while Humayun tried a call - the log showed Cloudflare's exact rejection reason, not just a bare status code. Fixed by making `cf()`'s body argument genuinely optional (no body, no Content-Type header, when omitted) and dropping the `{}` at the `/session/new` call site specifically. **Confirmed working - a real call connected successfully.**
- [x] **Also hardened `src/lib/connect.js` so any future non-2xx response from `worker-realtime` (502, 503, 401, ...) shows the worker's actual `error`/`detail` text in the app, not just a bare status code.** What this actually does in the app: before this, if a Connect call ever failed, the only thing shown was a generic message with a bare number (e.g. "Could not start Connect session (500)"), with no clue why - Humayun would have had to come back and ask what a bare status code meant every time. After this fix, that same failure instead surfaces the worker's own specific reason inline (e.g. "Could not start Connect session (500): Cloudflare Realtime session limit reached" or whatever the real cause is) - it's purely about making a *future* failure self-explanatory in the app itself, not something that changes any behavior when calls are working normally. This is also what made the `wrangler tail` log above so quickly conclusive when diagnosing it. **Shipped in `blue-kite-ops-round7-connect-fix.zip` alongside the worker fix above - the worker half is confirmed deployed and working; whether `connect.js` has been committed to GitHub and built into a fresh installer yet is unconfirmed, see Notes.** The exact same code is present in every `connect.js` shipped since (including round 8.5/8.6 batch 2's `connect.js`), so applying that file at all carries this forward.
- [x] **Operational lesson worth keeping in mind for every future Cloudflare Worker fix:** `npx wrangler deploy` deploys whatever is in the `worker-realtime`/`worker-r2` folder **on Humayun's own computer's disk** - it has nothing to do with GitHub. Editing a worker's source file only through the GitHub website (as done for every other file, since that's what GitHub Actions builds from) does NOT get picked up by a local `wrangler deploy` unless that same file is also updated locally on disk first. This caused one full round of "the fix didn't work" that was actually just stale local code being redeployed unchanged. Worth flagging plainly next time a Worker file changes: it needs updating in **two** places (GitHub, for the Actions build; local disk, for `wrangler deploy`), not one.

### Round 8 (2026-09-22) - dependencies, delete/archive, and two real display bugs

Six items came in as one batch; this round covers all six. Scope was agreed with Humayun up front (permanent delete **and** archive for both clients and episodes/main tasks; true multiple dependencies, not just one) before any of it was built.

- [x] **True multiple dependencies per task/step.** A step (and every task an episode generates from it) can now wait on any number of other steps at once, not just one - the "Depends on" picker on both the Workflows page and a template's Add-step flow is now a multi-select checklist instead of a single dropdown. New `tasks."dependsOnStepIds"` jsonb array column (**schema_v8.sql**); the old single-value `"dependsOnStepId"` column is left in place, unused, same pattern as `dependsOnLabel` before it - nothing generated before this round loses its existing dependency, it just reads as a one-item list until its template step is edited again. The "is this task blocked" check now requires **every** prerequisite to be done, not just one, and the "Waiting on: ..." label lists all of them. Cycle detection was rewritten from a simple chain-walk into a real graph search, since a loop can now form through any combination of multiple dependencies, not just a single A-waits-on-B-waits-on-A chain.
- [x] **Root cause found for "I add a dependency and it doesn't show up on the workboard."** This is a genuine two-part explanation, not just "the multi-dependency work above fixes it":
  1. The generic Board page (My Board / "all open tasks") was never checking dependencies at all - only the single episode-detail checklist page was. Fixed: the Board page now computes the same blocked/greyed-out state as the episode page, for every task it lists.
  2. **This is the one to know about going forward:** a dependency is baked into a task at the moment its episode is generated from the template - it is not looked up live from the template every time the page loads. So changing a step's dependency on the Workflows page only affects **episodes generated after that change** - an episode that already existed (last month's "Guest Episode," for instance) keeps whatever dependency (or lack of one) it was given when it was created, even after you edit the template. **Resolved round 8.5 (see below) - Humayun asked for this to apply retroactively, and it now does.**
- [x] **Workflow step drag-to-reorder wasn't working.** Real bug, and a well-documented one: on Windows, Tauri's webview intercepts the OS's own native file-drag-and-drop by default, which silently swallows the browser's in-page HTML5 drag events too (the app's own reorder code was already correct - this was never a JS bug). Fixed with one line in `src-tauri/tauri.conf.json` (`"dragDropEnabled": false`), which is Tauri's documented way to hand drag-and-drop back to the webview. Reordering steps on the Workflows page now also updates every open episode's checklist and the Board immediately, since step order was already read live rather than baked in. **Confirmed working by Humayun.**
- [x] **Ctrl+scroll-wheel zoom / screenshot too small to read.** Also a genuine, separate bug from the zoom hotkeys fixed in round 6: those all worked, but TimeLog's screenshot detail view was rendering the image in its own plain, non-zoomable `<img>` tag instead of reusing the app's existing full-featured lightbox. Fixed by wiring the screenshot detail view into that same lightbox. **Confirmed working by Humayun, but the lightbox's own panning/Reset were still broken - see round 8.5 below for the real fix.**
- [x] **"Could not find the 'custom' column of 'tasks' in the schema cache" adding a custom task to a one-off episode.** Straightforward miss, not a design issue: the app has always tried to write a `custom` flag when adding a custom task, but the `tasks` table never actually had that column - nobody had tried adding one until now. One-line fix in **schema_v8.sql**.
- [x] **No way to delete a task, and no separate "Completed" section.** Each task on the episode checklist now has a delete button (Manager/Admin only) - confirms first, then removes the task and everything attached to it (comments, links, attachments cascade via the existing foreign keys, no schema change needed). Completed tasks now move into their own "Completed" section at the bottom of the checklist instead of staying mixed in with open ones. **Confirmed working by Humayun.**
- [x] **Still can't remove an already-added client.** Both options Humayun asked for are built, for clients **and** for episodes/main tasks: **Archive** (reversible) and permanent **Delete**. New `clients.archived` / `episodes.archived` boolean columns, **schema_v8.sql**. **Confirmed working by Humayun.**
- [x] **Exit confirmation "still doesn't confirm or give a warning," even on a build that has the round-6 fix.** A real, separate bug: `window.confirm()` is well-documented to silently fail to render inside a Tauri/WebView2 app specifically when triggered from an async event that didn't originate as a direct click - exactly what the window's "X" button close does. Fixed by switching just this one dialog to Tauri's own native dialog plugin (`@tauri-apps/plugin-dialog`'s `confirm()`), already a project dependency - no new package needed, just one added permission (`dialog:allow-message`). **Confirmed working by Humayun.**

### Round 8.5 (2026-09-23) - Phase 2, batch 1 of 3 (dependencies retroactive, zoom rebuild, cancel invites)

Phase 2 restructured at Humayun's request into two halves: new fixes/features first, the multi-role rebuild second (see the renamed Phase 2 section below). Given the size, sequenced into 3 batches - this is batch 1, the smaller self-contained pieces; batch 2 (accept-required calling + ringtone) and batch 3 (multi-role) are still to come.

- [x] **Dependency edits now apply retroactively, everywhere, immediately** - the decision flagged as open at the end of round 8. Both the episode checklist and My Board now look a task's dependency up LIVE off the CURRENT template step (`liveDepStepIds()`, new), instead of the fixed copy baked into the task when its episode was generated. Editing a step's dependency in Workflows now shows up on every episode already on the board, not just ones generated afterward. Falls back to the old baked-in value when there's no live template step to check (a custom task, a one-off episode, or a step since deleted from the template) - fails open rather than losing the dependency. **Confirmed working by Humayun 2026-09-24** ("Dependencies added in workflow nav reflect back on the workboard").
- [x] **Rebuilt image zoom with real click-and-drag panning; fixed Reset.** Root cause of both "very glitchy" and "Reset doesn't work": the old zoom only ever set a CSS `transform: scale(...)` on the image and relied on the container's native scrolling to pan around once zoomed - but a transform doesn't grow an element's scrollable area, so there was genuinely nothing to scroll to. Zooming in just visually grew the image from its corner and clipped whatever fell outside the frame with no way to reach it. Rebuilt to drive zoom AND pan through the same transform in JS instead (`translate(panX,panY) scale(zoom)`), with real click-and-drag (pointer events, so a drag tracks correctly even if the cursor leaves the image mid-drag) and pan clamped so the image can never be dragged fully out of view. Reset now zeroes pan together with zoom, and zooming back down to 100% via any method (buttons, hotkey, Ctrl+wheel) snaps pan back to centered automatically, not just an explicit Reset click.
- [x] **Cancel a pending invite.** Real gap, not a UI oversight: `invites` had row-level security enabled but no delete policy defined for it at all, so cancelling was impossible at the database level no matter what the app offered. New **schema_v9.sql** adds a delete policy scoped the same as the existing read/create ones (Admin any invite, Manager their own team's only), restricted to invites that haven't been used yet. Cancel button added next to every pending invite on both the Team Settings and Admin pages. **Confirmed working by Humayun 2026-09-24.**

Phase 2's plan below is corrected accordingly: no "primary role" concept is needed anywhere.

### Round 8.6 (2026-09-23) - Phase 2, batch 2 of 3 (accept-required calling + soft ringtone)

- [x] **Accept-required calling for anyone clocked out, plus a soft ringtone.** Scope confirmed with Humayun before building: calling someone who's currently clocked IN is completely unchanged - still the original instant-connect-no-accept behavior (`phase-2-requirements.md`'s decisions log). Calling someone who's clocked OUT now shows them a real Accept/Decline popup instead of pulling them straight into the call; they either accept (joins the call room normally) or decline/let it ring out (hangs it up on the caller's end). **Confirmed working by Humayun 2026-09-24** - "the new calling ringtones works flawlessly... calling is now flawless" (apart from a still-untested 3+-person group call, see Still Open).
  - **Why this needed a brand-new signal, not just UI:** Connect's call state has always been Presence-based (`src/lib/connect.js`) - everyone on a call tracks their own presence in a shared "call room," and someone's presence appearing/disappearing IS the join/leave signal. That already covers ACCEPT for free (accepting just joins the room like before). But there was never any signal at all for DECLINE or TIMEOUT - the caller would just sit on "Calling..." forever with no way to know the other side said no or never looked at their screen. Added a new `'ring-missed'` broadcast event (`declineRing()`, new export in `connect.js`) sent on the callee's per-user channel specifically to cover those two cases.
  - **Two independent safety nets, not just one:** the callee's popup sends `'ring-missed'` explicitly on Decline and again automatically after a 30-second on-screen countdown times out. But in case that message is ever missed (app closed mid-ring, network hiccup), the CALLER also runs its own independent ~38-second fallback timer (30s ring + 8s grace) that gives up and hangs up on its own if nobody has actually joined the room by then, regardless of whether the explicit signal arrived. Either signal alone is enough to end the wait cleanly.
  - **Soft ringtone, synthesized rather than sourced.** Rather than bundling a licensed/downloaded audio file (a real asset-licensing risk for a commercial app), the ringtone is a two-note chime generated live in JS with the Web Audio API (`AudioContext` + `OscillatorNode` + a `GainNode` envelope for a soft attack/decay, no harsh clicks) - regenerated fresh each ring and cleanly torn down afterward. This also means Phase 6's planned move to self-hosted audio for the music player has zero bearing on this - it's a wholly separate, tiny synthesized cue, not a music file.
  - Ring timeout: ~30 seconds, as confirmed. No new schema/database change needed for any of this - it's built entirely on the existing ephemeral Realtime broadcast channels, so there's no schema_v10.sql for this batch.

### Round 8.9-fix (2026-09-27) - the 3 batch A items Humayun's test found broken, root-caused and fixed for real

Same standard as every round in this project: root cause first, not a guess-and-ship patch. All three were genuinely different bugs, unrelated to each other.

- [x] **Launch-on-startup - replaced the whole approach, not patched.** Root cause: this app's own `src-tauri/windows-app-manifest.xml` makes it request UAC elevation (`requireAdministrator`) on *every* launch - added a phase or two back for reliable global keyboard/mouse capture. A registry Run-key entry (what `tauri-plugin-autostart`'s `enable()` actually sets up) is fundamentally incompatible with that: `explorer.exe` is what processes the Run key at logon, and `explorer.exe` can never silently elevate a child process on someone's behalf - there isn't even an interactive desktop yet at that point for a UAC prompt to appear on. So Windows just quietly refuses to start it. The registry entry itself is real (which is exactly what Task Manager's Startup tab was showing as "Enabled"), but the process behind it never actually runs - a textbook case of the setting looking on while doing nothing. **Fix:** dropped `tauri-plugin-autostart` (removed from `src-tauri/Cargo.toml` entirely - no autostart crate needed at all any more) in favor of a Windows **Scheduled Task** with an `ONLOGON` trigger and "Run with highest privileges" (`schtasks.exe /Create /F /SC ONLOGON /RL HIGHEST ...`), called directly from `src-tauri/src/main.rs`'s `.setup()` hook via `std::process::Command`. That specific combination is the standard, documented way to autostart something that needs elevation - the task itself is pre-authorized at CREATE time (by this already-elevated process), so it launches at logon with no interactive UAC prompt at all. Recreated (`/F`, force-overwrite) on every launch, so it's automatically idempotent and self-repairing, and it also keeps the target `.exe` path current if a future update ever moves the install to a new folder. No console window flashes when it runs (`CREATE_NO_WINDOW`).
- [x] **Comment count - found the actual gap: it only ever refreshed on a TASK change, never a COMMENT change.** The batch A version's count query ran inside the same listener that watches the `tasks` table - which means it only re-ran when a task itself changed (checked off, added, deleted). But posting, editing, or deleting a comment only ever writes to the `taskComments` table, never `tasks` - so nothing ever told the page "a comment just changed, go recount." The very first count fetch on a fresh page load should have shown any comments that already existed, but from then on the badge could never advance without some unrelated task change forcing a re-render - which is exactly "count never shows" from the perspective of someone opening a discussion, posting a comment, and closing it again expecting to see a number. **Fix:** added a second, independent live subscription on `taskComments` itself (same "global table subscription, filtered query on each refetch" pattern already used everywhere else in this file) that re-fetches and re-renders the badge counts on ANY comment add/edit/delete, anywhere - not just when a task changes. This also covers the follow-up ask (a hidden/collapsed discussion should still hint whether any communication happened) for free, since the count now actually updates live and shows in the collapsed button text either way, exactly as batch A originally intended.
- [x] **Cross-group step reorder - found the real interaction, a subtler bug than "reordering doesn't work."** A template's steps have always used ONE flat, global `order` sequence across the WHOLE template (not scoped per group) - dragging a step just reassigns sequential order numbers to every step in its new position. That's fine for ordering steps *within* a group against each other. The bug was in how the episode checklist decided which GROUP HEADER shows first: it used to just take groups in whatever order their first step was hit while walking that flat sequence - so if you dragged one step from Group A to a position ahead of ALL of Group B's steps (to reorder just that one step), Group A's first-encountered position could jump ahead of Group B's, dragging Group A's *entire header* - every other step in it, untouched by the drag - ahead of Group B's on every episode's checklist. Exactly Humayun's description: "the entire group gets reordered instead of just that one step." **Fix:** added a new, separate, append-only field on each template - `groupOrder`, a plain list of group names - that records the HEADER order independently of any individual step's position, and is only ever touched when a genuinely new group name is introduced (adding a step with a new group, via `openAddStepModal`), never by a plain reorder. The episode checklist now reads header order from `groupOrder` instead of inferring it from step order, so a step drag can only ever move that one step - it can never drag its whole group's header position along with it. A template saved before this shipped self-heals its `groupOrder` automatically (derived from its current step order, a one-time catch-up write) the next time anyone views its client's Workflow templates section or the Workflows nav page. **Needs `supabase/schema_v11.sql` run first** (adds the `groupOrder` column to `templates`) - **important: apply the SQL before the code this time**, since the code's `groupOrder` writes would otherwise fail outright and break "Add step" too (not just silently skip the new field) until the column exists.
- **Not yet confirmed by Humayun** - all three passed static verification (`node --check` on `main.js`; Rust checked by hand for brace/paren balance and argument types, since this sandbox can't compile Rust against crates.io) but none has been run against a real build yet.

**Apply order for this round:** run `supabase/schema_v11.sql` in the Supabase SQL editor **first**, then apply `src/main.js`, `src-tauri/src/main.rs`, and `src-tauri/Cargo.toml` on GitHub, in that order if possible (SQL before code, same reasoning as above).

## Phase 2.5 - polish batch, requested 2026-09-26 (scope being finalized)

Eight items, requested as one batch right after confirming all of Phase 2 (batches 1-3) works. Humayun explicitly asked whether this is too much for one phase and invited splitting it up - proposed breakdown below, pending answers to a few real ambiguities before any of it is built.

**Quick investigation already done on four of these (to size them accurately, not yet fixed):**
- **Back button disappearing on a client's page (item 4):** root cause found. `renderClient()`/`renderEpisode()` write their main content straight to `app.innerHTML` instead of going through the shared `paint()` helper - and `paint()` is the ONLY place that prepends the back button. So the back button briefly shows during the loading skeleton (which does use `paint()`), then vanishes the instant the real client/episode data loads. Small, well-understood fix.
- **"Hide discussion" doing nothing (item 5):** root cause found. It's a pure CSS bug, not JS - `.task-collab{...display:flex...}` in `style.css` has higher specificity than the browser's built-in `[hidden]{display:none}` rule, so setting the `hidden` attribute (which the JS already does correctly) has no visible effect. One CSS line fixes it (`.task-collab[hidden]{display:none;}`).
- **Reordering workflow steps not affecting already-placed tasks (item 3, third bullet):** root cause found. Each task's display order (`orderNum`) is baked in at the moment it's created and read back with `.orderBy('orderNum','asc')` - it is NOT looked up live from the template's current step order the way dependencies now are (`liveDepStepIds()`). So dragging steps into a new order on the Workflows page updates the template, but every already-generated episode keeps showing tasks in their old order. Same shape of bug as the dependency-retroactive fix from round 8.5 and the new-step backfill from round 8.7 - fixable the same way.
- **Single .exe output (item 6):** the workflow currently builds both NSIS and MSI installers (`--bundles nsis,msi`) and uploads them as a GitHub Actions "artifact," which GitHub always serves as a .zip when downloaded from a run's Artifacts tab - that's a GitHub platform behavior, not something in our control. Dropping `msi` from the build args gets down to one installer, but the *download itself* will still be a small zip **unless** the build instead publishes to a GitHub Release (which serves each attached file raw, no zip) - the workflow already supports this for a tag push (`tagName`/`releaseName` are conditional on `github.ref_type == 'tag'`), just needs Humayun to push a version tag instead of only pushing to `main` for a "final" build.
